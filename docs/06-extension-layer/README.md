## 3. 核心概念

### 3.1 扩展层的职责

扩展层是 piagent 的**插件化扩展框架**，其核心职责是：

| 职责 | 说明 |
|------|------|
| **扩展 API** | 为扩展提供标准化的 `ExtensionAPI` 接口，封装内核能力 |
| **扩展发现** | 自动扫描指定目录，发现并加载扩展文件 |
| **扩展加载** | 动态导入扩展模块，执行其初始化函数 |
| **隔离保障** | 单个扩展加载失败不影响其他扩展和主流程 |

### 3.2 设计理念：扩展优先

piagent 强调"扩展优先"的设计理念：

1. **内核最小化** — 核心功能保持精简，非核心功能通过扩展提供
2. **不修改内核** — 扩展不需修改 piagent 核心代码，通过 API 接口操作
3. **动态加载** — 扩展在运行时被发现和加载，支持热插拔
4. **一等公民** — 扩展与内核的交互方式标准化，与内置模块享有同等能力

### 3.3 扩展能做哪些事

通过 `ExtensionAPI`，扩展可以：

| 能力 | 方法 | 说明 |
|------|------|------|
| 注册工具 | `registerTool()` | 添加自定义工具，供 LLM 调用 |
| 注销工具 | `unregisterTool()` | 移除已注册的工具 |
| 注册命令 | `registerCommand()` | 添加 CLI 可调用的命令 |
| 监听事件 | `on()` | 订阅 Agent 生命周期事件 |

### 3.4 扩展加载优先级

扩展文件按以下优先级从高到低搜索：

```
CLI 指定路径  →  项目目录 .pi/extensions/  →  全局目录 ~/.piagent/extensions/
```

## 6. 小结

扩展层是 piagent 插件化架构的基石。通过 `ExtensionAPI` 和 `ExtensionLoader` 的组合，piagent 实现了"内核最小化、功能可扩展"的设计目标。扩展无需修改核心代码，通过标准化接口即可为 Agent 添加新能力，这使得 piagent 生态能够灵活生长。

### 思考题

1. 扩展层的设计为什么把 `ExtensionAPI` 和 `ExtensionLoader` 分离成两个类？
2. 如果想让扩展支持依赖注入（例如扩展 A 依赖扩展 B 提供的工具），加载器需要做哪些改动？
3. 扩展的 `on()` 方法订阅了 Agent 事件，但扩展本身没有 `unsubscribe` 的返回方法——这是设计缺陷吗？如何改进？
