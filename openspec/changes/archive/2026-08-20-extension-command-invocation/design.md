# 扩展命令调用入口 — 设计

## Context

见 proposal.md「Why」:扩展命令有注册面无调用面。`ExtensionAPI` 已通过 `registerTool`/`registerCommand`/`on`/`listCommands`/`getCommand` 暴露;本设计只补**消费端**——把用户交互输入路由到已注册扩展命令,不改变扩展注册机制与既有的工具执行路径。

约束:依赖注入优先、UI 与核心解耦(见 config.yaml context);纯增量,不引入新 runtime 依赖。

## Goals / Non-Goals

- 目标:交互输入命中扩展命令时执行之并回显结果;提供可枚举命令的可见入口。
- 非目标:不做命令参数解析 DSL,不做历史/补全,不改动扩展注册与加载协议,不改造模型调用路径。

## Decisions

- **决策:在交互输入处理处增加"先判命令、后走对话"的前置分发。**
  用户在 TTY/交互输入的内容仍默认作为 user 消息发给 Agent;仅当输入首词精确命中一个已注册扩展命令名时,才转去执行该命令。
  理由:保持普通对话行为零回归,扩展命令作为显式缺省前的特判。
  备选:把所有输入都尝试当作命令——被否,会劫持普通消息,破坏既有对话契约。

- **决策:命令结果直接打印到输出通道,不进入会话持久化或 LLM 上下文。**
  理由:扩展命令是用户侧的一次性工具操作,不属于对话历史;保持 session 消息模型不变。
  备选:把命令结果作为 user/assistant 消息入库——被否,会污染会话语义且引入额外分支。

- **决策:用 `ExtensionAPI.getCommand` 作为唯一查找入口,命令查找是纯查询无副作用。**
  理由:无需触碰命令存储结构,复用既有 API,改动面最小。

## Risks / Trade-offs

- [输入首词撞名普通对话] → 命中判定仅发生在精确匹配已注册命令时;撞名概率低且命令行上下文有明确分隔前缀,误判影响可控。
- [命令 execute 抛错] → 捕获异常并打印错误信息,不使交互循环崩溃;与既有工具执行错误处理风格一致。

## Migration Plan

纯增量、无数据迁移,无回滚风险。
